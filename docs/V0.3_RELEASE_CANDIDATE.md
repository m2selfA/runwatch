# runwatch v0.3.0 Release Candidate Contract

Status: **qualified 2026-09-05; publication pending annotated tag + GitHub Release (R19)**.

## Product scope

v0.3.0 preserves runwatch's single-writer durable-authority architecture and publishes the post-v0.2 durable multi-Attempt lifecycle together with the already-qualified desktop-attention improvements. `runwatchd` remains canonical for Run/Attempt/Observation/Delivery state, scheduler and Local Process lifecycle, SSH observation, continuation delivery and Retry allocation/submission. GUI/MCP/CLI remain clients of that authority.

The release includes:

- immutable per-Run Attempt history and attempt-scoped lifecycle evidence;
- daemon-owned, idempotent Human Retry for eligible Failed/Cancelled unbound Runs;
- crash/restart and ambiguous scheduler-receipt recovery without duplicate scientific execution;
- reviewed scheduler resource overrides on Retry while logical Run identity remains fixed;
- GUI Attempt selector/history, attempt-scoped Observation/Logs/Artifacts and Run-global Timeline;
- WindUI 0.15 dynamic tray summaries projected from canonical DashboardSnapshot state;
- GUI-local, versioned notification/display preferences and coalescing policy that remain disposable UX state;
- existing Windows Human Run Console, manual Local/Slurm/LSF Run submission, service controls and responsive Hosts surface;
- Windows package/visual CI and Linux glibc-2.17 runtime artifact gates.

v0.3.0 does **not** enable controller-originated native OS background notifications. crates.io WindUI 0.15.0 lacks the required public runtime `TrayHandle::notify` path; runwatch therefore leaves those controls visibly disabled rather than using a private fork or raw Win32 tray handles. Upstream `huanfeng/wind-ui-rust#13` is tracked separately and is not a release blocker.

## Compatibility contract

v0.3.0 keeps local IPC:

```text
protocol_version = 1
service          = runwatchd
storage          = sqlite-wal
```

Compatibility remains capability-based; `hello.version` is diagnostic. The SQLite schema is **3**. Opening an existing schema-2 v0.2 store creates the durable `retry_intents` table in place and advances metadata to schema 3; regression explicitly covers that path. Existing v0.2 Attempt lifecycle paths remain authoritative and are not rewritten. New executions use attempt-scoped `<workspace>/.runwatch/<run_id>/attempt-N/` lifecycle directories.

Human Retry is intentionally conservative: only the current Failed/Cancelled Attempt of a human/unbound Run is eligible. Any durable continuation binding or residual agent/session/project identity fails closed. Changed command/workspace/runner/host semantics require a new logical Run rather than Retry.

## Upgrade contract

Supported in-place upgrade remains:

1. close the tray GUI;
2. use the old package's `runwatch.exe autostart --remove` to quiesce/stop/unregister the owned resident runtime;
3. replace the entire sibling package directory;
4. run the new package's `autostart --install`, `daemon-status`, then Pi `runs_doctor` as applicable.

Stopping runwatch observation is not scientific Run cancellation. The v0.2 upgrade qualification already proved active scheduler work survives whole-package replacement and is rediscovered from the canonical store; R17 additionally qualifies schema-2 -> schema-3 opening and changed retry durability under crash/restart.
